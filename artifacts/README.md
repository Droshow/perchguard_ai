# Architecture

Taking the concept of Admission Control — traditionally used in Kubernetes to govern what enters a cluster — and applying it to Agentic Workflows represents a powerful architectural pivot. In an agentic ecosystem, the "attack surface" isn't just a malicious user; it's an autonomous agent that might hallucinate a destructive command, be manipulated via prompt injection, or simply exceed its intended scope.

Below is how PerchGuard can be transformed into a "Line of Defense" for the agentic era.

## The PerchGuard Framework: Admissions for Agents

In this model, PerchGuard acts as a transparent proxy/interceptor between the Agent (the "Brain") and the Environment (the "Tools").

### 1. The Validation Layer (The "No-Go" Zone)

Just as Kubernetes admission controllers check whether a container has "root" privileges, PerchGuard checks whether an agent's proposed action violates safety boundaries.

- **Prompt Injection Detection:** Scans the incoming user prompt and the agent's internal monologue for "jailbreak" patterns before any tool is triggered.
- **Semantic Firewalling:** Uses a smaller, faster model to verify that the agent's intended tool call (e.g., `delete_database`) matches the user's original intent.

### 2. The Mutation Layer (The "Safety Net")

Sometimes an agent's request is mostly fine but needs a nudge.

- **Parameter Sanitization:** If an agent tries to run a CLI command, PerchGuard automatically injects `--dry-run` or strips dangerous flags like `-rf /`.
- **Least Privilege Injection:** Automatically appends constraints to a SQL query generated by an agent to ensure it only accesses the specific user's row.

### 3. The Resource Quota Layer (Preventing "Agentic Sprawl")

Agents can loop. A loop that calls a paid API 10,000 times is a "denial-of-wallet" attack.

- **Token/Cost Budgets:** PerchGuard tracks the cumulative cost of a specific agentic "session" and kills the process if it exceeds a threshold.
- **Max Depth Enforcement:** Prevents "Agent-calling-Agent" recursions from spiraling out of control.

## The "Line of Defense" Architecture

| Feature | K8s Admission (Original) | Agentic Admission (The Pivot) |
| --- | --- | --- |
| Object | YAML Manifests | Tool Calls / Tool Outputs |
| Trigger | `kubectl apply` | LLM Response (Action) |
| Verification | Signature / Schema check | Intent / Safety Alignment |
| Outcome | Allow / Deny / Mutate | Execute / Block / Ask for Human |

## Strategic Advantage: The "Perch" Metaphor

The name PerchGuard works perfectly here. It implies a high-level vantage point where the security layer:

- **Sees the whole forest:** Has context of the entire conversation history.
- **Stays out of the fray:** Doesn't interfere with the agent's "thinking" process until the moment of action.
- **Swoops in:** Only intervenes when a policy is triggered, minimizing latency.

## How This Guards Against "Agentic Attacks"

If a malicious actor uses indirect prompt injection (placing a hidden instruction on a website the agent reads), the agent might think it's supposed to exfiltrate data. PerchGuard's Outbound Admission Policy would detect an agent trying to `POST` to an unknown URL and block it, regardless of how "convinced" the agent was that it should do so.
